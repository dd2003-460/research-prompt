## retest-32k 修正（关键发现）

R0.5 在 max_tokens=16000 下 3/3 全崩，初判为"模型指令遵循随机性"。
但 R0.3 的 run 输出 30-36K chars 却完整收尾，暗示 16000 token 上限可能引入截断噪声。

retest-32k 对照实验（固定 prompt/temp，只改 max_tokens=32000）：
- runA：完整收尾（五节 5/5 + SELF-CHECK 覆盖全部 4 叶子节点）
- runB/runC：仍停草稿

崩塌率从 3/3 降到 2/3。**崩塌与 max_tokens 配置交互，非纯模型随机。**

修正后结论：
- R0.5 的"全面崩塌"部分归因于 max_tokens=16000 的截断效应
- R0.6 的 run1 崩塌（6分）同样可能在 32000 下改善
- 跨版本比较必须统一 max_tokens，否则混入截断噪声

## 最终结论

**R0.3 仍是 qwen3.8-27b 上的最优 prompt 变体（17.33/σ0.94），消融实验到此终止。**

证据链：
1. R0.3 的三防崩机制（语言锁定/占位符FAIL/逐卡表）在 ×3 run 中全部生效，σ=0.94 受控。
2. 任何在此基础上叠加新契约的尝试（R0.5 加 S3、R0.6 加 S3+C2）都引入了显著崩塌概率。
3. R0.4 证明 S3 SELF-CHECK 方向正确（遵循时 S3 1→2），但无法保证遵循。
4. 崩塌归因修正：非纯模型随机，与 max_tokens 配置交互（16000 下更严重）。
5. 后续消融轮次已统一 max_tokens=32000（服务器上限 32768），消除截断噪声变量。

## 后续提升路径（非 prompt 层面）

- 换更强的执行模型（如 70B+ 或 API 模型）可突破此边界
- 分步执行（先出结构再填内容）可能比单 prompt 多契约更稳定
- 外部验证器（跑完后检查契约是否满足，不满足则重试）比 prompt 内约束更可靠
- 统一 max_tokens=32000 是最低成本的稳定性提升（已落地）
