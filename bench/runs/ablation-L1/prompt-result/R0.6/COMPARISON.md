## 关键发现

### 1. R0.3 在 32k 下完美稳定（σ=0）
三 run 全 18 分，五节结构完整，逐卡表齐全，C2 从 1.67 升到 2.00。
三防崩机制（语言锁定/占位符FAIL/逐卡表）在 32k 下依然全部生效。
**R0.3 是 qwen3.8-27b 上的最优 prompt 变体，消融实验到此终止。**

### 2. R0.5 在 32k 下仍 3/3 崩塌
retest-32k 初判"崩塌与 max_tokens 交互"被推翻：
- run1：中文草稿流（6分）
- run2/run3：纯英文草稿流（0分），连基本结构都没有
- 不是截断问题，是模型对 S3 SELF-CHECK 契约的随机失守

### 3. 崩塌归因最终结论
- **非 max_tokens 截断**（32k 下 R0.5 仍崩）
- **非 prompt 设计缺陷**（R0.3 的三防崩在 32k 下完美）
- **是模型能力边界**：qwen3.8-27b 对多契约长 prompt 有 ~30-100% 概率随机失守
- 加第 4 个契约（S3）或第 5 个（C2）会触发这种随机性，无法通过 prompt 工程消除

## 后续提升路径（非 prompt 层面）

1. **换更强的执行模型**（70B+ 或 API 模型）— 突破模型能力边界
2. **分步执行**（先出结构再填内容）— 降低单 prompt 契约密度
3. **外部验证器**（跑完检查契约是否满足，不满足则重试）— 比 prompt 内约束更可靠
4. **max_tokens=32000 统一** — 已落地，消除截断噪声变量
