## 根因分析

### run1 崩塌 (18→10)
- S1=0: 树形分解缺失（R-x.y.z 结构不完整）
- 输出 41913 chars（最长），模型"跑飞"到计算细节，丢失了报告骨架
- 机械检查：五节标题全在(5/5)，但内容组织崩塌
- **与 R0.4 run1 同模式**：额外指令分散注意力 → 格式契约执行失败

### C4 全面归零 (1→0)
- R0.3 的 C4=1 来自模型对 GPU 保值率的"常识性提及"（A100 保值、消费卡掉价快）
- R0.7 四列要求把注意力拉向计算精度，模型不再做定性市场判断
- **C4 本质是知识注入问题**（SUMMARY §3.4），prompt 强化其他维度会挤占 C4 注意力

### C2 未提升 (2→1.67)
- run2/run3 的 C2 维持 2（四列满足）
- run1 的 C2 降到 1（drift 声明缺失——模型写了瓶颈分析但没用 "compute-bound→bandwidth-bound 漂移" 的精确措辞）
- **结论**：C2=2 不是 prompt 不够强，是模型能力上限。R0.3 已经拿到满分。

## 判读

**R0.7 负面结果确认**：
1. +107B 改动足以触发 run1 崩塌（概率 ~33%，与 R0.4 的 ~33% 一致）
2. C2 天花板 = 2（模型已满分，强化无收益）
3. C4 是注意力竞争受害者（强化计算维度 → 挤占市场判断）
4. **R0.3 的 18/20 确实是当前模型+任务的最优平衡点**

## 最终结论（更新 SUMMARY §5）

R0.3 定版不变。任何 prompt 修改（+4行 SELF-CHECK / +1.2KB 附录 / +107B C2 强化）都触发崩塌或维度退化。
**突破 18 分需要换更强执行模型（70B+/API 级），而非继续调 prompt。**
